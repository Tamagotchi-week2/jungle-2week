# 다마고치 웹게임 — 설계 문서

> 기획 명세서를 구현 관점에서 확정한 문서. 숫자(밸런스 상수)는 프로토타입 이후 조정 대상.

## 1. 개요

- 장르: 레트로 다마고치 육성 및 수집 시뮬레이션
- 목표: 4종의 알을 부화·진화시켜 **24종 성체 도감** 완성
- 플레이 필드: **마을을 직접 돌아다니는 캐릭터 조작** (방향키 이동 / 스페이스 상호작용)
- 자원: 농사 · 광산 · 어업으로 직접 채집한 음식이 **진화 방향을 결정**
- 수집 요소: 부화 시 **1% 확률 알비노** (도감 금테)
- 소셜: 3차 성체를 유저 간 1:1 교환 (개체당 1회 한정), 우편함의 전역 방명록
- 진입: **로그인 필수** — 미인증 상태로는 게임에 들어갈 수 없다

### 게임 루프

```
마을 이동 → 채집(논·광산·해안가) → 집에서 먹이기
  → 먹인 음식 종류가 성향 결정 → 2차·3차 진화
  → 성체 완성 → 도감 등록 + 보상 알 획득 → 반복
  → 부족한 칸은 다른 유저와 교환
  (우편함에서 전역 방명록 열람·작성)
```

## 2. 진화 규칙

### 2.1 단계

| 단계 | 명칭 | 비고 |
|---|---|---|
| 0 | 알 | 공 / 육 / 해 / 금 |
| 1 | 유아기 | 부화 시 1% 알비노 판정 |
| 2 | 성장기 | 성향 X ∈ {a, b, c} 로 분기 |
| 3 | 성체 | 성향 Y 판정 후 `sort(X, Y)` 조합 확정 |

### 2.2 조합 공식

```
최종 성체 조합 = sort(X, Y)   // X: 2차 확정 성향, Y: 3차 확정 성향
```

`ab`는 a→b, b→a 양쪽 경로에서 도달 가능(대칭).

- X = a → aa, ab, ac
- X = b → ab, bb, bc
- X = c → ac, bc, cc

### 2.3 24종 매핑

| 조합 | 공 (조류) | 육 (육상) | 해 (해상) | 금 (금색) |
|---|---|---|---|---|
| aa | 오목눈이 | 호랑이 | 고래 | 유니콘 |
| ab | 닭 | 고양이 | 흰동가리 | 티라노 |
| ac | 대머리수리 | 멧돼지 | 아귀 | 구미호 |
| bb | 펭귄 | 개 | 해달 | 용 |
| bc | 타조 | 판다 | 해마 | 돌고래 |
| cc | 황조롱이 | 코끼리 | 킹크랩 | 공작 |

## 3. 성향 시스템 (a / b / c)

성향은 **먹인 음식의 종류**로 결정된다. 음식은 유저가 직접 채집한다.

| 채집 활동 | 산출 자원(음식) | 성향 |
|---|---|---|
| 농사 | 작물류 | **a** |
| 광산 | 광물류 (동굴버섯·수정 등 식용 형태) | **b** |
| 어업 | 어패류 | **c** |

### 판정 규칙

- 먹이 1회 = 해당 성향 +1점
- **2차 분기**: 유아기 누적 먹이 `N = 10`회 도달 시, 최다 성향을 X로 확정
- **3차 분기**: 성장기 누적 먹이 `M = 15`회 도달 시, 최다 성향을 Y로 확정
- **동점 처리**: **동점 그룹 중** 가장 마지막에 먹인 성향을 채택
  - 예: `a=4, b=4, c=2` 이고 마지막이 `c` 라면, c는 동점 그룹이 아니므로 무시하고 a·b 중 더 나중에 먹인 쪽을 택한다
  - 단순히 "마지막에 먹인 성향"으로 두면 위 경우가 정의되지 않는다. 10회·15회 모두 동점이 실제로 발생 가능하다
  - 유저가 의도적으로 조정 가능하다는 성질은 유지된다

### 단계 전환 시 카운터 리셋 (필수)

**2차 판정과 3차 판정은 서로 다른 구간을 본다.**

```
유아기: trait 카운터 0에서 시작 → 10회 누적 → X 확정 → 카운터 전부 0으로 리셋
성장기: trait 카운터 0에서 시작 → 15회 누적 → Y 확정
```

리셋하지 않으면 3차 판정이 25회 누적으로 계산되어 **X와 Y가 사실상 항상 같아진다.** 그 결과 `aa` · `bb` · `cc` 만 나오고 `ab` · `ac` · `bc` 6종이 도달 불가능해진다. 진화 엔진 테스트에 이 케이스를 반드시 포함한다.

> 성장 진행도의 기준은 **시간이 아니라 먹인 횟수**다. 시계 조작으로 성장을 앞당길 수 없다.

### 3.1 채집 방식

세 채집은 각각 다른 상호작용을 가진다.

| 채집 | 상호작용 | 산출 |
|---|---|---|
| **농사** | 씨앗을 뿌리고 **120초 대기** 후 수확. **1구획** | 12개 |
| **광산** | **35회 연타** (스페이스바) | 1개 |
| **어업** | **QTE** 타이밍 입력 (스페이스바) | 성공 2개 / 실패 0 |

- 씨앗은 별도 아이템으로 두지 않는다 (무제한). 아이템화하면 경제가 불필요하게 복잡해진다
- 밭은 **1구획**. 무제한으로 심을 수 있으면 "120초에 12개"라는 제약이 무의미해져 농사가 나머지를 압도한다
- 주기가 **120초**인 이유는 조작 빈도와 이동 비용이다. 짧은 주기는 다시 신경 써야 하는 간격이 잦고, 마을 필드(4장)가 추가되면서 논까지 왕복하는 비용까지 붙었다. 수확량을 함께 올려 **분당 산출 6.0개는 유지**하면서 논 방문 빈도만 낮췄다
- **농사 대기 120초 동안 광산·어업을 병행할 수 있다.** 대기가 빈 시간이 되지 않고, 세 채집을 섞어 쓰는 것이 최적 플레이가 되어 성향 편중도 완화된다
- **부작용 — 초반 체감.** 첫 수확까지 2분이 걸리고 12개씩 뭉텅이로 들어오므로, 순수 a 빌드의 이론 완성 시간은 4.2분이지만 실제로는 수확 단위에 걸려 6분(3회 수확)이 된다. 게임 시작 직후 논에 먼저 심어두는 것이 자연스러운 동선이 되도록 튜토리얼을 설계해 완화한다
- 어업 QTE 실패 시 산출 0. 이는 육성 실패(6장의 "실패 없음")와 무관한 채집 결과일 뿐이다

#### 서버 검증

| 채집 | 검증 방식 |
|---|---|
| 농사 | `planted_at` 을 서버 시각으로 저장 → 수확 요청 시 120초 경과 여부 검증 |
| 광산 | 시작/완료 2단계 요청. 서버가 **최소 소요 시간 하한**을 검증 (예: 연타당 80ms) |
| 어업 | 서버가 입질 시각을 결정 → 클라이언트는 입력 사실만 전송 → 서버가 도착 시각으로 판정 (3.2 참조) |

QTE 성공 여부를 클라이언트가 그대로 주장하게 두면 조작이 쉽다. 자원 가치가 낮아 과잉 방어는 불필요하지만, 위 구조는 비용 없이 최소한의 검증을 제공한다.

### 3.2 어업 QTE 상세

#### 상호작용 (반응형)

```
1. 캐스팅       유저가 스페이스로 낚시 시작
2. 입질 대기    랜덤 3~9초 (예측 불가해야 한다)
3. 입질 신호    찌 움직임 연출 + 사운드
4. 판정         신호 후 제한시간 내 스페이스 입력 시 성공
```

타이밍 바를 목표 구간에 맞추는 방식도 가능하나 **반응형을 택한다.** 반응형은 "언제 클릭했는가"가 곧 판정이라 서버가 자기 시계만으로 검증할 수 있는 반면, 바 방식은 바의 위치가 클라이언트 상태라 서버가 검증할 대상이 없다.

#### 통신 구조

```
POST /api/fish/cast
  서버: bite_delay = random(FISH_BITE_DELAY_MIN ~ MAX)
        cast_at(서버 시각)과 함께 gather_sessions 에 저장
  응답: bite_delay  (클라이언트 연출 타이밍용)

POST /api/fish/strike
  서버: 반응시간 = (요청 도착 서버 시각 - cast_at) - bite_delay
  판정: 반응시간 < FISH_MIN_HUMAN_MS  → 실패 (봇)
        0 ≤ 반응시간 ≤ FISH_QTE_WINDOW_MS → 성공, 자원 2개
        윈도우 초과 → 실패
  세션 resolved 처리 (재사용 불가)
```

**클라이언트는 "성공했다"고 주장하지 않는다.** 입력했다는 사실만 전송하고 판정은 전적으로 서버가 수행한다.

#### 방어 범위

- **막는 것**: 성공 결과 위조, 세션 재사용, 응답 조작을 통한 무한 획득, 비인간적 반응속도
- **못 막는 것**: 정교한 자동 클릭 봇. 입질 신호를 클라이언트가 렌더링하는 이상 스크립트는 정확한 타이밍을 알 수 있으며, 서버 스트리밍 없이는 원리적으로 차단 불가능하다. 자원 가치가 낮으므로 **여기까지를 적정선으로 둔다.**

#### 네트워크 지연

서버가 측정하는 반응시간에는 왕복 지연이 포함되어 지연이 큰 유저가 불리하다. 판정 윈도우를 체감 목표보다 **약 300ms 넉넉히** 잡아 흡수한다 (체감 400ms 난이도 → 서버 윈도우 700ms).

#### 입질 대기 시간이 밸런스를 결정한다

분당 10.5개는 **1회 시도 8초**를 전제로 한 값이다.

```
캐스팅 0.5s + 입질 대기 평균 6.0s + 반응 0.5s + 결과 연출 1.0s ≈ 8s
```

입질 대기를 2–5초(평균 3.5초)로 줄이면 1회 시도가 5초가 되어 **분당 16.8개**가 되고 어업이 혼자 압도한다. 따라서 입질 대기는 **3–9초(평균 6초)** 를 유지해야 한다. 낚시는 기다리는 행위라는 점에서 감각적으로도 자연스러우며, 그동안 농사가 돌고 있으므로 빈 시간이 아니다.

### 3.3 산출량 밸런스

음식이 성향을 결정하므로, 세 채집의 분당 산출량 차이가 그대로 **특정 성체의 도달 난이도**가 된다.

**설계 원칙**

- 농사 = 수동 소득. 병행 가능해 사실상 공짜 → 분당 산출 **최저**
- 광산 = 단순 반복. 시간과 손가락을 소모 → **중간**
- 어업 = 실패 리스크 + 타이밍 요구 → 분당 산출 **최고**

**단, 세 채집은 서로 경쟁하지 않는다.** 각각 다른 성향의 자원을 산출하므로 유저는 "어느 쪽이 효율적인가"가 아니라 "지금 어떤 성향이 필요한가"로 선택한다. 따라서 분당 산출량 차이가 의미를 갖는 유일한 지점은 **각 빌드의 완성 시간**이며, 특정 채집만 필요한 유저(예: `aa` 목표)의 체감이 과도하게 나빠지지 않도록 격차를 관리한다.

**산출 근거** (스페이스 연타 **한 손 초당 5회**, 어업 1시도 8초, QTE 성공률 70% 가정)

| 채집 | 1회 산출 | 1회 소요 | 분당 회수 | 분당 산출 |
|---|---|---|---|---|
| 농사 (a) | 12개 | 120초 (병행) | 0.5회 | **6.0개** |
| 광산 (b) | 1개 | 35연타 ≈ 8초 | 7.5회 | **7.5개** |
| 어업 (c) | 2개 (성공 시) | 8초 × 70% | 7.5회 | **10.5개** |

**광산의 목표 연타 수가 유일한 실질적 제동 장치다.** 연타는 본질적으로 빠른 행동이라 목표치를 낮게 잡으면 광산이 혼자 압도한다.

#### 연타 속도 가정 — 한 손 기준

스페이스바 지속 연타는 자세에 따라 편차가 크다. **한 손 단일 손가락 기준 초당 5회**를 설계 기준으로 삼는다.

```
목표 1회 소요 = 8초
결과 연출 = 1초
→ 연타 시간 7초 × 5회/초 = 35회
```

한 손을 기준으로 삼는 이유는 **대다수 유저의 실제 자세이므로 중앙값이 목표치와 일치**하기 때문이다. 양손을 기준으로 잡으면 다수인 한 손 유저가 목표치에 미달한다.

**대신 상한이 열린다.** 양손 연타(초당 7회) 유저는 1회 6초로 줄어 분당 10개까지 나온다. 다만 어업(10.5개)을 넘지 않으므로 **"더 노력하면 더 얻되 최고 효율은 아니다"** 라는 형태가 되며, 허용 가능한 성질로 본다.

**35회를 확정값으로 사용한다.** 평균 추정치 기반이므로 구현을 막지 않는다. 플레이 후 조정이 필요하면 실측 연타 속도 `R`회/초를 대입해 `MINE_CLICK_TARGET = 7 × R` 로 재계산한다.

**검증 — 25회 먹이(성체 1마리) 기준 소요**

| 목표 조합 | 필요한 자원 | 소요 |
|---|---|---|
| `aa` (순수 a) | 작물 25 | 약 4.2분 |
| `bb` (순수 b) | 광물 25 | 약 3.3분 |
| `cc` (순수 c) | 어패 25 | 약 2.4분 |
| `ab` · `ac` · `bc` (혼합) | 두 종류를 단계별로 분리 | 약 1.9분 |

- `aa` 계열(오목눈이·호랑이·고래·유니콘)이 여전히 가장 느리지만 순수 c 대비 **1.75배** 수준이다. 농사만 하는 유저도 4분 남짓이면 성체 하나를 완성할 수 있다
- 광산의 35연타는 유지한다. 자원 종류가 달라 농사와 직접 경쟁하지 않으며, 이 제동 장치를 풀면 광산이 다시 혼자 튄다
- 농사의 실제 소요는 수확 단위(12개)에 걸려 계단식이 된다. 이론값 4.2분보다 길게 체감된다

#### "혼합이 효율적"의 정확한 의미

혼합이 빠른 것은 **자원 획득 속도**이지 육성 전략이 아니다. 두 축을 혼동하면 안 된다.

| 축 | 내용 |
|---|---|
| **자원 획득** | 농사를 심어두고 광산·어업을 도는 것이 항상 최적. 세 채집은 병행 가능하며 서로를 막지 않는다 |
| **먹이 선택** | 목표 조합이 결정한다. `cc` 를 노린다면 어패류만 먹여야 하고, 섞어 먹이면 목표 조합에 실패한다 |

즉 **모으는 것은 섞어서, 먹이는 것은 목적에 맞춰**가 정확한 표현이다. 혼합 조합(`ab` · `ac` · `bc`)을 노릴 때는 아무렇게나 섞는 것이 아니라 **유아기에는 한 종류, 성장기에는 다른 종류**로 단계를 분리해 먹여야 한다. 한 단계 안에서 섞으면 최다 성향이 흔들려 의도한 결과가 나오지 않는다.

## 4. 마을 필드와 조작

유저는 마을을 직접 돌아다니는 캐릭터를 조작한다. 각 시설에 가서 상호작용해야 해당 기능을 쓸 수 있다.

### 4.1 조작

| 입력 | 동작 |
|---|---|
| 방향키 상하좌우 | 이동 (타일 단위) |
| 스페이스바 | 바라보는 방향의 시설과 상호작용 |
| ESC | 열린 오버레이 닫기 |

**타일 그리드 이동을 사용한다. 자유 픽셀 이동이 아니다.**

- 충돌 판정이 "그 칸이 통행 가능한가" 배열 조회 한 번으로 끝난다
- 상호작용도 "바라보는 칸에 무엇이 있는가"로 끝난다
- 자유 이동을 택하면 AABB 충돌·미끄러짐·모서리 끼임을 직접 처리해야 하는데, 이 게임에서 얻는 것이 없다

미니게임 내부 입력도 **스페이스바로 통일**한다 (광산 연타, 어업 QTE). 마우스와 키보드를 오가지 않는다.

### 4.2 시설

| 시설 | 상호작용 결과 | 화면 |
|---|---|---|
| **집** | 다마고치 육성 화면 (먹이 주기, 상태 확인, 진화) | 오버레이 |
| **우편함** (집 앞) | 방명록 — 전역 게시판 열람 / 작성 | 오버레이 |
| **논** | 농사 — 심기 / 수확 | **필드에서 직접** |
| **광산** | 광산 — 스페이스 연타 | **필드에서 직접** |
| **해안가** | 어업 QTE | 오버레이 |

도감과 교환은 시설이 아닌 **전역 UI**로 둔다 (상단 바 등). 특정 장소까지 걸어가야만 도감을 볼 수 있으면 불편하기만 하다.

#### 논·광산은 오버레이를 열지 않는다

두 채집은 **마을 화면에 선 채로** 처리한다. 조작이 단순하고 반복 빈도가 높아, 매번 전체 화면이 열렸다 닫히면 번거롭기만 하다.

- **논**: 스페이스로 심기 / 수확. 결과는 짧은 피드백(예: "작물 12개")으로만 알린다
- **광산**: 스페이스 연타. 진행도는 **필드 위 작은 게이지**로 표시한다 (`0 / 35`)

**어업만 전용 오버레이를 쓴다.** 찌·입질 신호·판정 윈도우를 보여줘야 해서 마을 화면 위에 얹기 어렵다. 기다렸다 반응하는 성격상 화면이 전환되는 편이 몰입에도 맞는다.

> 서버 API 는 화면 형태를 알지 못한다. `plant`/`harvest`, `mine/start`/`finish` 요청만 받으므로,
> 이 결정은 순수하게 클라이언트 구현에만 영향을 준다.

### 4.3 렌더링 구조

**게임 엔진(Phaser 등)을 사용하지 않는다.** 물리·스크롤·적이 없는 단일 화면 마을에서 엔진이 주는 이점(타일맵, 아케이드 물리, 카메라)은 거의 쓸모가 없고, 도감·교환·육성 UI가 전부 React이므로 캔버스와 React 사이를 잇는 비용이 더 크다.

```
마을 (Canvas 2D 또는 DOM 그리드)
  ├ 필드 내 상호작용 — 논(심기·수확) / 광산(연타 게이지)
  └ React 오버레이 (activeScene 상태로만 연결)
       집 / 우편함 / 해안가 / 도감 / 교환
```

- 마을은 **스크롤 없는 단일 화면**. 카메라 로직이 통째로 사라진다
- 논·광산은 오버레이 없이 마을 화면에서 처리한다 (4.2)
- 그 외 시설은 스페이스 상호작용 시 전체 화면 오버레이로 열리고, 닫으면 마을로 돌아온다
- 마을과 오버레이는 서로를 알지 못하며 `activeScene` 하나로만 연결된다

### 4.4 맵 크기가 채집 밸런스에 영향을 준다

3.3의 산출량은 "논에 심어두고 광산을 돈다"를 **이동 비용 0**으로 계산한 값이다. 마을이 크면 논↔광산 왕복 시간이 실제로 소모되어 농사 효율이 떨어지고 밸런스가 무너진다.

- **시설 간 편도 이동이 3초를 넘지 않는 크기로 유지한다** (대략 15 × 11 타일 내외)
- 반대로 긍정적 효과가 더 크다. 농사 대기 120초 동안 광산에 다녀오는 흐름이 물리적으로 자연스러워지며, "병행이 최적 플레이"라는 기획 의도가 공간으로 표현된다

### 4.5 플레이어 위치는 서버가 검증하지 않는다

위치는 **연출 계층**이다. 서버는 플레이어가 실제로 광산 앞에 서 있었는지 확인하지 않으며, 자원 획득의 정당성은 기존 검증(3.1)으로만 판단한다. 위치까지 검증하려면 이동을 서버 권위로 만들어야 하는데, 자원 가치 대비 과잉이다.

### 4.6 플랫폼

방향키 조작을 전제하므로 **데스크톱 전용**이다. 모바일 대응이 필요하면 가상 D-pad가 추가로 필요하며, 1차 범위에서는 제외한다.

## 5. 시간 처리

시간은 **브라우저가 켜져 있는 동안에만** 흐른다. 시간이 관여하는 곳은 **농사의 120초 대기뿐**이다.

### 구현 방식

**heartbeat나 세션 시간 누적은 사용하지 않는다.** 채집 방식(3.1)이 모두 요청 시점에 검증 가능한 형태이므로 불필요하다.

- 농사: `planted_at` 을 서버 시각으로 저장하고, 수확 요청이 들어올 때 120초 경과를 검증
- 브라우저를 닫으면 수확 요청 자체를 보낼 수 없으므로 "켜진 동안에만 진행"이 자연히 지켜진다
- 광산은 대기 시간이 없다. 어업의 입질 대기(3–9초)는 **세션 내부의 대기**이며, 세션이 끊기면 그대로 무효가 되므로 별도 시간 관리가 필요 없다
- 성장 진행도는 시간이 아닌 먹인 횟수이므로 시간과 무관하다

부수 효과로 서버리스 요청량 문제도 발생하지 않는다.

### 실패 상태

**없음.** 방치로 인한 사망·성장 정지는 구현하지 않는다.

## 6. 알 / 개체 사이클

```
초기 지급: 가챠 4회 (종류 중복 가능)
동시 육성: 1마리
성체 완성 → 보상 알 1개 지급
```

**"동시 육성 1마리"의 정의**: `stage < 3` 인 개체가 계정당 최대 1마리다. 완성된 성체(`stage = 3`)와 교환으로 받은 성체는 개수 제한 없이 보유하며, 이 제약에 포함되지 않는다. 부화 요청 시 이 조건을 서버가 검증한다.

### 초기 알 가챠 (4회 독립 시행)

| 알 | 확률 |
|---|---|
| 공 | 30% |
| 육 | 30% |
| 해 | 30% |
| 금 | 10% |

- 종류 중복 가능. 4개 모두 같은 종류가 나올 수도 있다 (0.81%)
- 금색 알이 하나도 안 나올 확률 = `0.9^4 ≈ 65.6%` — 대부분의 유저는 금색 없이 시작한다
- 롤은 계정 생성 시 **서버에서 1회** 수행하고 결과를 영속화 (리롤 방지)

### 보상 알 획득 규칙

```
최초 성체 완성 1회 한정 → 금색 알 확정
그 이후:
  10%  → 금색 알
  90%  → 공 / 육 / 해 중 유저가 선택한 알
```

- 최초 지급 여부는 `users.first_adult_reward_claimed` 플래그로 관리 (계정당 1회)
- 롤과 알비노 판정은 **모두 서버에서만** 수행하고 결과를 즉시 영속화 (새로고침 리롤 방지)
- 교환으로 받은 성체는 보상 알을 지급하지 않는다

### 보상 알 획득 연출

결과와 무관하게 **항상 동일한 선택 화면**을 보여준다. 유저는 선택 전에 결과를 알 수 없다.

```
1. 공 / 육 / 해 3개의 알 이미지 제시 (평범한 상태)
2. 유저가 하나 선택
3. 금색 판정이었다면 → 선택한 알이 금색 알로 변화하는 연출
   일반 판정이었다면 → 선택한 알 그대로 확정
```

- 금색 확정 케이스(최초 성체 / 10% 롤)에도 **선택 화면을 건너뛰지 않는다.** 화면이 달라지면 선택 전에 결과가 노출되어 연출이 무의미해진다
- 금색 판정 시 유저가 무엇을 골랐는지는 결과에 영향을 주지 않는다 (선택은 연출용)

#### API 설계 (결과 사전 노출 방지)

```
POST /api/reward-egg/open
  → 서버가 롤 수행, 결과를 pending_reward 로 저장
  → 응답에는 선택지(공/육/해)만 포함. 판정 결과는 절대 포함하지 않는다

POST /api/reward-egg/claim { chosen: '공' | '육' | '해' }
  → 저장된 pending_reward 를 확정하여 인벤토리 반영
  → 응답으로 최종 알 종류(금색 여부) 반환 → 클라이언트가 연출 재생
```

응답 페이로드에 판정 결과를 미리 실으면 개발자 도구로 선택 전에 확인 가능하므로, **반드시 2단계 요청으로 분리**한다.

## 8. 도감

- **4열 × 6행 = 24칸** 그리드
- 서버(`GET /api/dex`)가 알 종류별 6칸씩 4묶음 순서로 내려주며, 클라이언트는 그 순서를 그대로 그린다
- 4열이므로 한 종류(6칸)가 1.5행을 차지해 행 경계와 맞아떨어지지 않는다. 종류별로 시각적으로 묶고 싶다면 열 단위 배치(`grid-auto-flow: column`, 6행)로 두어 **한 열 = 한 알 종류**가 되게 하는 편이 낫다
- 완성도 = `COUNT(has_normal OR has_albino) / 24` — **알비노 보유만으로도 해당 칸 완성 처리**
- 테두리 금색 = `has_albino`
- 카드 클릭 → 확대 뷰 → `알비노 보기` 버튼 → CSS 3D flip (`rotateY(180deg)` + `backface-visibility: hidden`) 으로 뒷면에 알비노 스프라이트
- 알비노 미보유 시 버튼은 비활성 상태로 노출 (수집 욕구 유발)
- 미획득 칸은 실루엣 처리

## 9. 교환

- **3차 성체만** 교환 가능. 자원·알은 교환 불가
- **개체당 1회 한정** — 성립 시 양쪽 개체 모두 `is_traded = true`, 이후 영구 교환 불가
- 교환 완료 시 양쪽 도감에 자동 등록. 등록 시 개체의 `is_albino` 를 반영해 `has_normal` / `has_albino` 중 해당 플래그를 켠다
- 상태머신: `제안됨 → 수락 / 거절 → 완료 / 취소`
- 1차 버전은 교환 코드 방식 (매칭 UI보다 구현 비용이 훨씬 낮음)

### 계정 기반 구조

교환은 **로그인 계정 간에 성립**한다. `trades.from_user` / `to_user` 가 `users.id` 를 참조하고, 소유권도 `pets.owner_id` 로 계정에 귀속된다. 교환 코드는 상대를 찾는 수단일 뿐이며, 소유권 이전 자체는 계정 대 계정이다.

**행위자는 반드시 서버 세션에서 도출한다.** 요청 바디에 담긴 `user_id` 를 신뢰하면 타인 계정 명의로 교환을 성립시킬 수 있다. 모든 교환 엔드포인트는 세션의 사용자와 개체 소유자가 일치하는지 검증한다.

### 서버 검증 (필수)

- 3차 성체인가
- **세션 사용자**의 소유 개체인가 (요청 바디의 user_id가 아님)
- 이미 교환된 개체인가 (`is_traded`)
- 다른 교환 제안에 잠겨 있지 않은가

### 원자성

소유권 이전 + 양쪽 도감 등록을 **단일 트랜잭션**으로 처리. 중간 실패 시 펫 복제/증발이 발생한다.

## 11. 스프라이트 에셋

알 · 유아기 · 성장기 · 성체 · 알비노를 **모두 개별 에셋으로 제작**한다. 공용 스프라이트나 CSS 필터 대체는 사용하지 않는다.

### 물량

| 단계 | 종류 수 | 알비노 | 합계 |
|---|---|---|---|
| 알 | 4 (공/육/해/금) | 해당 없음 | **4** |
| 유아기 | 4 | ×2 | **8** |
| 성장기 | 4 × 3 (a/b/c) | ×2 | **24** |
| 성체 | 4 × 6 (조합) | ×2 | **48** |
| | | | **소계 84장** |

추가로 마을 필드용 에셋이 필요하다.

| 항목 | 수량 |
|---|---|
| 플레이어 캐릭터 (4방향 × 걷기 2–3프레임) | 8–12 |
| 마을 타일셋 (바닥·길·물·벽 등) | 10 내외 |
| 건물·오브젝트 5종 (집·우편함·논·광산·해안가) | 5–10 |
| | **소계 26–32장** |

**총 110–116장 내외.**

**알 단계는 알비노 구분이 없다.** 알비노는 부화 시점에 판정되며, 알 그림이 갈리면 부화 전에 결과가 노출되어 1% 연출이 무너진다.

### 경로 규칙

```
/public/sprites/egg/{eggType}.png                          → 4
/public/sprites/baby/{eggType}[_albino].png                → 8
/public/sprites/teen/{eggType}_{trait}[_albino].png        → 24
/public/sprites/adult/{eggType}_{combo}[_albino].png       → 48

/public/sprites/player/{dir}_{frame}.png                   → 8~12  (dir: up|down|left|right)
/public/sprites/tiles/{name}.png                           → 10 내외
/public/sprites/buildings/{house|farm|mine|shore}.png      → 4~8

eggType : air | land | sea | gold
trait   : a | b | c
combo   : aa | ab | ac | bb | bc | cc
```

경로는 `spritePath(stage, eggType, key, isAlbino)` 리졸버 함수로 계산한다. DB에 경로를 저장하지 않는다 — 규칙으로 도출 가능하므로 `species.sprite` 컬럼은 불필요하다.

### 규격

- 64 × 64 투명 PNG (레트로 톤에 맞춰 실제 도트는 32 × 32로 찍고 2배 확대)
- `image-rendering: pixelated`
- 팔레트 제한 (알 종류별 공통 팔레트 + 알비노용 팔레트)

### 제작 파이프라인

전량이 완성되기를 기다리면 개발이 멈춘다. 두 장치로 분리한다.

1. **플레이스홀더 자동 생성** — 전체를 스크립트로 생성해 **최종 파일명 그대로** 먼저 배치한다 (색상 블록 + 종 이름 텍스트). 아트가 완성되는 대로 같은 경로에 덮어쓰면 코드 변경이 0이다.
2. **에셋 존재 검증 테스트** — 모든 경로가 전부 존재하는지 확인하는 테스트를 둔다. 누락은 반드시 발생하며, 도달 난이도가 높은 조합(예: 황조롱이 알비노)에서 나면 발견이 매우 늦어진다.

### 알비노 제작 팁

요구사항은 개별 에셋이되, 제작은 **원본의 팔레트 스왑**으로 시작하면 작업량이 실질적으로 절반이 된다. 결과물은 여전히 독립된 파일이므로 이후 개별 수정이 자유롭다.

## 12. 기술 스택 (확정)

```
Next.js (App Router) + TypeScript      프론트/백 단일 저장소
Postgres (Neon) + Prisma               교환 트랜잭션, 도감 유니크 제약
Tailwind CSS + CSS keyframes           도감 그리드, 플립 카드, 변신 연출
Auth.js                                간이 로그인 1종만
TanStack Query                         서버 상태 캐싱
Vitest                                 진화 엔진 테스트
Vercel                                 배포
```

### 선택 근거

- **게임 엔진(Phaser/PixiJS/Unity) 미사용.** 마을 필드가 추가되었지만 물리·스크롤·적이 없는 단일 화면 타일맵이라 엔진의 이점이 거의 없고, 나머지 UI가 전부 React이므로 캔버스와의 연결 비용이 더 크다. 상세 근거는 4.3 참조.
- **관계형 DB 필수.** 교환의 원자성과 도감 유니크 제약 때문에 문서형 DB(Firestore)는 부적합하다.
- **전역 상태 관리 라이브러리(Zustand 등) 미사용.** 모든 상태는 서버에 있고 클라이언트는 표시만 한다. TanStack Query 캐시가 곧 상태이며, 별도 스토어를 두면 진실이 두 개가 되어 동기화 버그만 늘어난다.
- 실시간 통신은 1차 버전에서 **3초 폴링**으로 대체 (필요 시 WebSocket 교체)
- 렌더링: 픽셀 폰트 + `image-rendering: pixelated` + 제한된 팔레트

### 서버리스 요청량

heartbeat를 사용하지 않으므로(5장) 주기적 요청이 없다. 서버 호출은 유저의 실제 행동(심기·수확·채집·먹이·교환) 시점에만 발생하며, 무료 티어에서 문제되지 않는다.

## 13. 개발 단계

**전제: 1–2주 / 소수 인원.** 여유가 없으므로 아래 범위 조정을 전제로 한다.

| 일차 | 내용 |
|---|---|
| 1 | 세팅 + Prisma 스키마 + Auth + **플레이스홀더 전량 생성** |
| 2 | **진화 엔진 + 24종 시드 + 불변식 테스트** (핵심) |
| 3–4 | 육성 루프: 부화 → 먹이기 → 성향 누적 → 2·3차 분기 |
| 5–6 | **마을 필드: 타일맵 + 이동 + 충돌 + 스페이스 상호작용 + 씬 전환** |
| 7–8 | 자원 채집 3종 + 인벤토리 + 서버 검증 |
| 9 | 도감 24칸 + 확대/플립 + 금테 |
| 10–11 | 교환 (트랜잭션 + 1회 제한) |
| 12 | 우편함 방명록(반나절) + 연출 + 배포 |
| 전 기간 | **아트 110장+ (별도 트랙, 병행)** |

마을 필드가 추가되며 **10일 → 12일**이 되었다. 2주 상한을 사용하거나 다른 항목을 줄여야 한다.

마을을 5–6일차에 배치한 이유는 채집 3종이 마을의 상호작용 위에 올라가기 때문이다. 마을 없이 채집 UI를 먼저 만들면 진입 경로를 나중에 다시 붙여야 한다.

2일차의 진화 엔진을 순수 함수 + 테스트로 먼저 굳혀두면, 이후 UI를 급하게 짜더라도 게임 규칙은 깨지지 않는다. 일정 압박의 안전판.

### 반드시 지킬 것 (게임의 정체성)

- 진화 엔진과 24종 매핑 — 데이터라 구현 비용이 거의 없다
- 알비노 1% + 도감 금테
- 교환 — 없으면 단순 육성 게임이 된다
- 보상 알 변신 연출 — 구현 비용 대비 체감 효과가 가장 크다

### 잘라낼 것

- 교환은 **교환 코드 방식**. 매칭 UI 없음
- 마을은 **스크롤 없는 단일 화면**. 카메라·미니맵·NPC 없음
- **모바일 대응 제외** (방향키 전제, 4.6)

> 채집 3종은 각각 다른 상호작용을 갖는다(3.1). 단, 연출·이펙트는 최소화하고 판정 로직만 먼저 구현한다.

> 스프라이트는 축소 대상이 아니다. 전량 개별 제작하며(11장 참조), 개발 트랙과 분리해 병행한다. 개발은 플레이스홀더로 진행하므로 아트 완성도가 일정을 막지 않는다.

### 2일차 불변식 테스트 (필수)

- X = a 에서 aa / ab / ac 만 도달 가능 (b, c 동일)
- 24종 전부 도달 가능
- 알비노는 1차 → 3차까지 유지
- `sort(X, Y)` 가 대칭 (a,b == b,a)

| 상수 | 초기값 | 비고 |
|---|---|---|
| `HATCH_ALBINO_RATE` | 0.01 | |
| `GOLD_EGG_RATE` | 0.10 | 보상 알 롤 |
| `STARTER_EGG_RATES` | 공30 / 육30 / 해30 / 금10 | 초기 가챠 |
| `STARTER_EGG_COUNT` | 4 | 초기 가챠 횟수 |
| `FIRST_ADULT_GOLD_GUARANTEE` | true | 최초 성체 완성 시 금색 확정 |

| `FEED_COST` | 1 | 먹이 1회당 자원 소모량 |
| `MAP_WIDTH` / `MAP_HEIGHT` | 15 / 11 | 마을 타일 수 (편도 이동 3초 이내) |

### 알려진 밸런스 이슈

- 성체 1마리 = 먹이 25회. 24칸을 혼자 채우려면 최소 600회 + 그만큼의 채집이 필요하다.
- 금색 알은 최초 1개 확정 후 10%로만 등장하므로, 금색 6종을 혼자 모으려면 기댓값상 **성체 50마리 이상**을 키워야 한다. 사실상 금색 6칸이 교환 수요의 핵심이 된다 (의도된 설계).
- 초기 가챠에서 금색이 안 나올 확률이 65.6%지만, 최초 성체 완성 시 금색이 확정 지급되므로 **모든 유저가 초반에 금색을 최소 1개 확보**한다. 초반 이탈 방지 장치로 기능한다.
- 3–4일차 육성 루프 완성 직후 실제로 1마리를 끝까지 키워보며 `STAGE2/3_FEED_COUNT` / `MINE_CLICK_TARGET` / `FISH_QTE_WINDOW_MS` 를 조정할 것. 특히 연타 속도와 QTE 성공률은 실측값이 가정과 다를 수 있으므로, 분당 산출량을 측정해 3.3의 목표치(6.0 / 7.5 / 10.5)에 맞춘다.
- **개발·시연 중에는 `STAGE2/3_FEED_COUNT` 를 반드시 낮춰 둘 것.** 25회 기준으로는 개발 중 테스트도 시연도 현실적으로 불가능하다. 환경변수로 전환 가능하게 구현한다.

## 16. 결론

### 이 문서의 상태

기획 명세서의 모든 공백이 확정값으로 채워졌다. **구현을 막는 미정 항목은 없다.** 추정 기반 상수 두 개(`MINE_CLICK_TARGET`, `FISH_QTE_WINDOW_MS`)는 플레이 후 조정 대상이지만, 확정값이 들어 있어 착수를 지연시키지 않는다.

### 설계를 관통하는 세 가지 원칙

구현 중 판단이 필요할 때 이 세 가지로 되돌아온다.

**1. 서버가 상태의 유일한 진실이다.**
모든 난수(알비노 1%, 초기 가챠, 보상 알)는 서버에서만 굴리고 즉시 영속화한다. 클라이언트는 결과를 주장하지 않고 행위만 보고한다. 성장 진행도를 시간이 아닌 먹인 횟수로 정의한 것, QTE 판정을 서버 도착 시각으로 하는 것 모두 같은 원칙에서 나왔다.

여기에는 **행위자 식별**도 포함된다. 모든 엔드포인트는 누가 요청했는지를 **세션에서 도출**하며, 요청 바디의 `user_id` 를 신뢰하지 않는다. 교환·먹이·채집·방명록 전부에 동일하게 적용된다.

**2. 규칙은 순수 함수로, UI와 분리한다.**
진화 엔진(`sort(X, Y)`, 성향 판정, 카운터 리셋)은 DB·UI를 모르는 순수 함수여야 한다. 일정이 압박받아 UI를 급하게 짜더라도 게임 규칙은 깨지지 않는다. 이것이 전체 일정의 안전판이다.

**3. 밸런스 수치는 전부 상수 테이블에 있다.**
채집 산출량은 서로 맞물려 있다. 하나를 바꾸면 특정 성체의 도달 난이도가 바뀐다. 코드에 숫자를 흩뿌리지 않는다.

### 착수 순서

```
1일차   세팅 · 스키마 · Auth(로그인 게이트) · 플레이스홀더 전량
2일차   진화 엔진 + 불변식 테스트   ← 여기가 심장
3일차~  육성 → 마을 → 채집 → 도감 → 교환 → 연출
```

**2일차를 절대 건너뛰지 않는다.** 진화 엔진은 데이터와 순수 함수뿐이라 하루면 끝나고, 여기가 굳으면 이후 어떤 UI 작업도 게임 규칙을 훼손할 수 없다.

### 구현 중 특히 주의할 지점

| 항목 | 위치 |
|---|---|

### 알려진 트레이드오프 (의도된 것)

- **금색 6칸은 혼자 모으기 어렵다.** 기댓값상 성체 50마리 이상이 필요하며, 이것이 교환 시스템의 존재 이유다.
- **`aa` 계열이 가장 느리다.** 순수 c 대비 1.75배. 대신 조작이 거의 필요 없는 수동 플레이다.
- **자동 클릭 봇은 막지 못한다.** 클라이언트가 신호를 렌더링하는 이상 원리적으로 불가능하며, 자원 가치를 고려해 방어하지 않는다.
- **모바일을 지원하지 않는다.** 방향키 조작 전제.

## 17. 부록 — 화면과 절차

본문에서 원칙만 정한 항목의 구체 절차. 이 문서만으로 착수 가능하도록 채워둔다.

### 17.1 인증 — 로그인 필수 (과제 요구조건)

**최초 화면은 로그인이며, 로그인 없이는 게임에 진입할 수 없다.**

```
/login   최초 진입 화면. 로그인 / 가입
   ↓ 성공
/game    마을 화면
```

- 미인증 상태로 `/game` 및 모든 API에 접근하면 `/login` 으로 리다이렉트한다. **미들웨어에서 일괄 처리**한다
- 게스트 모드·체험 플레이는 없다. 교환과 방명록이 계정을 전제하므로 익명 상태가 존재할 수 없다

**Auth.js Credentials 방식 하나만 사용한다.**

- 가입/로그인: **닉네임 + 비밀번호** (이메일 없음, 비밀번호는 bcrypt 해시)
- OAuth를 쓰지 않는 이유: 앱 등록·리다이렉트 URI 설정이 필요해 1–2주 일정에서 순손실이다
- 닉네임은 유니크. **교환 상대와 방명록 대상을 식별하는 유일한 표시 이름**이다
- 가입 성공 시 서버가 **초기 알 가챠 4회를 즉시 굴려 영속화**한다 (6장)

**모든 서버 로직의 행위자는 세션에서 도출한다.** 클라이언트가 보낸 `user_id` 는 어떤 경우에도 신뢰하지 않는다 (9장).

### 17.2 집 — 육성 화면

```
[스프라이트]  현재 개체 (알 / 유아기 / 성장기 / 성체)
              알비노면 금테 프레임으로 표시

[정보]        단계, 진행도 "7 / 10회"
              성향 카운터  a 3 · b 4 · c 0

[먹이 버튼]   작물 (a)  |  광물 (b)  |  어패 (c)
              각 버튼에 보유 수량 표시. 0이면 비활성

[상태]        진화 가능 시 "진화" 버튼 노출
```

**스탯 시스템은 존재하지 않는다.** 배고픔·청결·행복도·체력 게이지를 만들지 않는다. 방치해도 아무 일이 일어나지 않으며(5장), 개체의 상태는 오직 **단계 · 진행도 · 성향 카운터** 세 가지뿐이다. 다마고치라는 장르 통념 때문에 스탯 바를 추가하기 쉬우나, 이 게임에는 그것을 소비할 시스템이 없다.

성향 카운터를 그대로 노출하는 이유는 목표 조합을 겨냥해 먹이려면 현재 분포를 알아야 하기 때문이다. 숨기면 유저가 조합을 통제할 수 없다.

### 17.3 HUD (마을 상시 표시)

- 자원 3종 보유량
- 알 인벤토리 (종류별 개수)
- `도감` · `교환` 버튼 — 전역 UI이므로 어디서든 열린다 (4.2)

### 17.4 교환 절차

상태머신(9장)에 대응하는 실제 흐름이다.

```
1. A가 교환할 성체 선택 → 6자리 교환 코드 발급        [제안됨]
   코드 유효 시간 10분. A의 해당 개체는 잠금 처리

2. B가 코드 입력 → A의 제안 개체 확인 → 자기 성체 선택
   B의 개체도 잠금 처리

3. A가 최종 수락 / 거절                                [수락 / 거절]

4. 수락 시 단일 트랜잭션으로:                          [완료]
   - 소유권 상호 이전
   - 양쪽 is_traded = true
   - 양쪽 dex_entries 등록 (is_albino 반영)
```

- 코드 만료 또는 거절 시 양쪽 개체의 잠금을 해제한다
- B가 코드를 입력하는 시점과 A가 수락하는 시점 사이에 개체 상태가 변할 수 있으므로, **트랜잭션 직전에 4개 검증(9장)을 다시 수행**한다
- 코드는 혼동되는 문자(0/O, 1/I)를 제외한 대문자·숫자 조합

### 17.5 튜토리얼 (최소 사양)

별도 시스템을 만들지 않는다. **첫 진입 시 안내 문구 3개**로 충분하다.

1. 최초 로그인 직후 — "논에 씨앗을 심어두면 돌아다니는 동안 자랍니다" (농사 120초 대기를 초반부터 돌리게 만드는 것이 목적)
2. 첫 부화 후 — "먹인 음식의 종류가 진화 방향을 결정합니다"
3. 첫 성체 완성 후 — 보상 알 연출로 자연히 이어지므로 문구 없음

`users` 에 `tutorial_step` 정수 컬럼 하나로 관리한다.

### 17.6 우편함 — 방명록 (과제 요구조건)

**전역 게시판이다.** 모든 유저가 같은 목록을 읽고 쓴다. 우편함은 그 게시판에 접근하는 **상호작용 지점일 뿐**이며, 유저별 수신함이 아니다.

집 앞 우편함에서 스페이스로 상호작용한다.

```
[방명록]   작성자 닉네임 · 내용 · 작성 시각  (최신순)
           내가 쓴 글은 내가 삭제할 수 있다

[작성]     메시지 입력 → 등록
```

대상 지정이 없으므로 닉네임 조회·수신자 개념이 존재하지 않는다. 다른 유저의 마을을 방문하는 기능도 필요 없다.

#### 제약

| 항목 | 값 |
|---|---|
| 메시지 길이 | 200자 |
| 작성 빈도 | 1분 1회 (계정 기준) |
| 삭제 권한 | **작성자 본인** |
| 표시 개수 | 최신 50개, 그 이상은 페이지네이션 |

- 작성자는 **세션에서 도출**한다. 요청 바디의 작성자 정보를 신뢰하지 않는다
- 삭제 시에도 세션 사용자와 `author_user_id` 일치를 검증한다
- React가 기본 이스케이프하므로 XSS는 자동 방어되지만, **`dangerouslySetInnerHTML` 을 쓰지 않는다**는 원칙을 유지한다
- 전역 게시판이므로 폴링으로 갱신한다. 우편함 오버레이가 열려 있는 동안에만 10초 간격으로 조회하고, 닫으면 중단한다
